# README （高齢者専用）　　ミズモ　〜 水分摂取習慣化・見守りアプリ〜

## 1.サービス概要
「ミズモ(水+メモ)」は、医療現場での原体験から生まれた高齢者特化型の水分摂取・見守りWebアプリ。若者向けアプリの複雑なUIを排除し、トークン認証による自動ログインや高齢者の身体特性に合わせた巨大UIを実装することで、自力での継続が困難だったシニア層の習慣化と、周囲の安心・安全な見守りを両立させます

## 2.このアイデアはどこから生まれたか
### 2-1.きっかけとなった体験・感情
- いつ・どんな状況で：
医療機関で働いていた時、夏場になると発熱で搬送される高齢者が急増する状況を何度も目にしてきた
特に印象的だったのは、高齢の患者様がよく『そういえば、あまり水分を取っていなかった』と話していた
実際、身近な高齢者も水分摂取不足により、体調を崩したことがあった

- どんな気持ちになったか：
発熱があると、コロナウイルスやインフルエンザの可能性を考慮し、隔離や感染対策を行う必要がある
検査で陰性が確認されるまで、感染対策を継続する必要がある
その時、私は「もし水分補給を習慣化できていれば、この患者様は熱中症にならず、医療機関の逼迫も予防できたのではないか」と強く感じた
2025年（令和7年）の統計では、熱中症の救急搬送者数は年間10万人で、そのうち65歳以上の救急搬送は全体の約6割（総務省）に及んでおり、この問題は個人の問題ではなく、医療現場全体の課題だと実感した

### 2-2.なぜそれが「気になった」のか
- 自分の性格、過去の経験
医療現場で働いていた経験から、「予防できる病気で医療機関が逼迫する」という状況に強い違和感を感じていた
高齢者は体温調節機能の低下、認知機能や判断力の低下により、水分摂取を忘れやすい傾向にある
しかし、「水分補給を忘れないようにする」という習慣化さえできれば、熱中症は予防できると考えた

- 大切にしている価値観：
私は「予防できる病気は予防すべき」という考えを大切にしている
特にコロナ禍以降、医療機関では感染対策の負担が増しており、「予防できる病気を減らすことで、医療現場の負担を軽減したい」という思いが強くあった
家族と一緒に住んでいても日中独居高齢者、完全独居高齢者が自宅で体調を崩してもなるべく早期発見できるようにしたい
また、医療現場で働いていた時に、「もっと早く対策できていれば」と感じる場面を何度も経験したことが、このアプリを作りたいと思った理由である

### 3-２.高齢者の特徴
加齢による身体的変化
（みんなの介護:https://www.minnanokaigo.com/news/kaigo-text/home-care/no503）
  - 指先の感覚の変化：加齢で乾燥した指ではスマホを操作しても反応しにくい
  - 細かい操作の困難性：小さなアイコンを正確にタップやスワイプ操作の開始位置、終了位置を正確にコントロールできない
  - 視力の低下：画面の小さな文字や細かいアイコンが見えにくい
ミズモの設計で注意する点
  - 文字を大きくする
  - ボタンを大きくして押しやすくする
     
### 3-3.認知症について
（健康ねっと:https://www.mcsg.co.jp/kentatsu/dementia/2464f）
（なかまぁる:https://nakamaaru.asahi.com/article/14889125）
MCI（軽度認知障害）:
 - 物忘れによって日常生活で多少支障が出る状態
認知症
 - 物忘れが悪化して日常生活に支障が出て、自立して生活するのが難しくなっている状態
記憶の種類
  - 記憶の保持期間：即時記憶　＞　短期記憶　＞　長期記憶 の順に失われる
    - 即時記憶：数秒〜数十秒ほどの直前記憶。最も早く消える
    - 短期記憶：数分〜数時間ほどの比較的短時間の記憶。認知症初期から障害される
    - 長期記憶：数年〜数十年以上前の遠隔記憶。認知症中期〜後期まで残る
  - 記憶の内容:エピソード記憶　＞　意味記憶　＞　手続き記憶　の順に失われる
    - エピソード記憶：個人の体験や出来事全般の記憶。体験が丸ごと消える
    - 意味記憶：言語の意味、知識、概念の記憶。中期以降に徐々に低下
    - 手続き記憶：体で覚えた運動・操作の記憶。最も長く残る
ミズモでアプローチする部分
  - 認知症の発症前に『手続き記憶（体で覚えた習慣）』として水分摂取を定着させておくことで、発症後も身体の感覚としてそのルーティンを維持しやすくする

### 3-4.表に見えている困りごと
どんな生活場面で困るのか：
  - 高齢者は「喉が渇いたら飲めば良い」と思っているが、喉の渇きを感じにくいため、気づいたときには頭痛やめまいなどの脱水症状が出ていることがある
  - 他者が「水飲んだ？」と声掛けしても、「さっき飲んだ」と答えるが、実際には飲んでいないこともある
  - 日中独居または完全独居高齢者の場合、熱中症になっても、気づかれない可能性が高い

何が不便なのか：
  - 水分摂取を記録するアプリはあるが、記録を忘れてしまう
  - 記録を忘れると、達成状況が正しく反映されず、アプリの価値が下がる
  - 他者が毎回声掛けするのは負担が大きい

なぜ困るのか：
  - 水分摂取を忘れると、脱水症や熱中症のリスクが高まる
  - 特に夏場は、気づかないうちに脱水状態になり、救急搬送されるケースも多い
  - 高齢者は喉の渇きを感じにくいため、意識的に水分摂取を行う必要がある
  - 医療機関の逼迫にもつながる

なぜWebアプリで解決する必要があるのか：
  - メール通知またはLINE通知により、定期的に水分摂取を思い出せる
  - 記録が自動的に残り、カレンダーで達成状況を視覚的に確認できる
  - 家族が遠方にいても、達成状況を共有できる(将来的な展開)
  - スマートフォンやパソコンがあれば、どこでも使える
  - 見守り家電は年金暮らしの高齢者にとっては高額

なぜ「声掛け」ではなく「メール通知」なのか：
  - 背景として独居高齢者の増加である
  - 高齢者は最もメール通知を使用する
  - 他者の声掛けに依存せず、個人で解決できる仕組みが必要である

- 「声掛け」と「メール通知」の違い：
| 比較項目 | 声掛け | メール通知（このアプリ） |
|---------|-------------------|---------------------|
| 継続性 | 家族の負担が大きく、継続が難しい | 自動化されているため、継続しやすい |
| タイミング | 家族の都合に左右される | 決まった時間に確実に届く |
| 記録の正確性 | 口頭のため、記録が残らない | アプリで記録が残り、振り返りができる |
| 心理的負担 | 「また言われた」という抵抗感がある | 機械的な通知のため、抵抗感が少ない |
| 達成感 | 達成状況が可視化されない | カレンダーで達成状況を可視化できる |
| 家族の負担 | 毎日声をかける必要がある | 家族の負担がなくなる |

なぜ「声掛け」では曖昧になるのか:  
  - 家族が「水飲んだ?」と聞いても、高齢者は「さっき飲んだ」と答えてしまうことがある
  - これは、記憶が曖昧であったり、家族を安心させたいという気持ちから、曖昧に答えてしまう
  - 記録が残らないため、本人も家族も「実際に飲んだかどうか」を確認できない

なぜ「メール通知」なら曖昧さが減るのか:
  - メール通知は「行動のきっかけ」を提供する
    - 「水を飲む」という行動を思い出すタイミングを提供する
  - 記録が残るため、曖昧さがなくなる
    -  目標達成をカレンダーで確認することができる
    - 「さっき飲んだ」という曖昧な回答ではなく、記録として残る
  - ワンタップで記録できるため、記録のハードルが低い
    - 既存アプリのように、飲料の種類や量を選ぶ必要がない
    - メールのリンクをタップするだけで、記録が完了する

MVPリリース後に検証したいこと:
  - 時間の都合上、今回はメール通知ではなく、携帯のアラーム通知を使用する
  - 携帯のアラームで「通知による習慣化」の検証を行う
  - 固定時刻の通知でも習慣化に役立つか
  - 記録が残ることで、「今日は飲んだ」が明確になるか
  - ログイン画面を経由する操作が、高齢者にとって負担になるか確認する

### 3-5.本当に解決したい課題は何か
- なぜ水分摂取を忘れるのか？
  - 加齢により、喉の渇きを感じにくくなりやすくなる
- なぜ喉の渇きを感じにくいのか？
  - 加齢により、体の水分量が減少し、喉の渇きを感じる機能が低下しているからである
- なぜそれが問題なのか？
  - 水分不足が続くと、脱水症や熱中症などのリスクが高まり、健康を損なうからである
- 本当に解決したい課題
  - 高齢者が、喉の渇きを感じなくても、定期的に水分摂取を思い出し、習慣化できるようにする

## 4.想定ユーザーについて
### 4-1.想定しているユーザー
年齢設定：
- 年齢：
  - 65歳〜75歳の比較的元気な高齢者
- 理由：
  - 熱中症による救急搬送の6割が65歳以上であり、この年代にアプローチすることで、熱中症予防に大きな効果が期待できる
  - 65歳〜75歳はスマートフォンやメールを日常的に使っている方が多いため、アプリの導入ハードルが低い
  - 今後、独居高齢者の割合が増加すると予測されている
  - 独居高齢者は家族の声掛けに依存できないため、自己完結で使えるアプリが必要である
  - 軽度認知障害（MCI）の発症前に、飲水習慣を身につけることで、長期記憶にアプローチできるのではないかと考えた
  - 軽度認知障害（MCI）までは携帯を利用できる可能性があるため、この層も対象に含めたいと考えた

ITリテラシー：
- スマートフォンやメールを日常的に使える方
- メールのリンクをタップして、簡単な操作ができる方

健康状態：
- 飲水制限がない方
- 軽度認知障害（MCI）までの方
- 比較的元気で、日常生活を自立して送れる方

生活環境：
- 独居または日中独居の方
- 家族の声掛けに依存できない環境にある方

ターゲットユーザーの明確化：
- 実際に毎日使うのは誰か：
  高齢者本人がメール通知を受け取り、ワンタップで記録を行う。
- 誰が導入・サポートするのか：
  完全独居の高齢者本人が自力で初期設定を行うのは困難な場合は、初期フェーズでは家族、または連携する介護事業所のケアマネジャーなどの周囲の人々に初期設定（メールアドレス・通知設定）を代理で行う設計とする
  ※詳細は第11章ビジネスモデル参照
- 毎日使うのは誰か：
  高齢者本人が毎日使う
  メール通知を受け取り、ワンタップで記録を行う
- 継続を支えるのは誰か：
  高齢者本人がメール通知とカレンダーの達成感によって継続できる仕組みにする
  家族を含む周囲の人々は、毎日の声掛けやサポートは不要である
  ただし、通知がない時は、高齢者の状況確認を行う必要がある

なぜ高齢者本人が自力で継続できるのか：
  - メール通知により、定期的に水分摂取を思い出せる
  - ワンタップで記録できるため、操作が簡単
  - カレンダーで達成状況を確認できるため、達成感が得られる
  - 家族を含む周囲の人々の声掛けに依存せず、アプリの仕組みで習慣化できる

環境設定：
- 環境：
  - メール通知を採用する
- 理由：
  - 高齢者の中には、LINEやスマホアプリに不慣れな方も多くいる
  　一方で、メールはフィーチャーフォン（ガラケー）時代から使い慣れている方が多い
  　スマホに機種変更した後もメールアプリは標準でインストールされているため、導入のハードルが低い
  　ただし、将来的にはLINE通知にも対応することで、より幅広く使ってもらえるようにしたいと考えている

### 4-2.自分とユーザーの距離
  - 医療現場での経験から、「水分を取り忘れていた」と話す高齢者を何度も見てきた
  　また、自分の家族にも高齢者がいるため、「将来的に身近な人にも使ってもらいたい」という思いが強くある

### 4-3.実際に使われる可能性について（需要・存在確認）
まず最初に使ってくれそうな人は誰か？
  - 自分の家族や親戚の高齢者、知人など、身近な高齢者にまず使ってもらいたいと考えている
その人は、どんな場面でこのアプリを思い出すか？
  - 「いつ、水を飲んだかな？」と不安になったとき、またはメール通知を受け取ったときである
今の生活の中で、代わりに使っているものは何か？

### 6-1.ユーザーの変化
行動や気持ちの変化：
MVP後:
1. 通知で水分摂取を思い出せる
  - 家族の声掛けに依存せず、定期的に水分摂取を思い出せる
  - 「今、水を飲もう」という行動のきっかけを提供する
2. ワンタップで記録できるため、記録が続けやすい
  - 携帯のアラーム後に、ログインするだけで、記録画面に遷移できる
  - 既存アプリのように、飲料の種類や量を選ぶ必要がない
  - 記録のハードルが低いため、継続しやすい
3. １週間の記録を見ることで達成状況を視覚的に確認できる
  - 「今日も達成できた」という小さな達成感が継続のモチベーションになる
  - 達成状況を一目で確認できるため、習慣化の進捗を実感できる

その先に期待できる変化:
 - 短期的変化（数週間〜数ヶ月）:
  - 水分摂取が習慣化される
    - 「喉が渇いたら飲む」から「時間になったら飲む」という行動変化
    - 1日の水分摂取回数が増え、目標水分摂取量を達成できるようになる
 - 中期的変化（数ヶ月〜1年）:
  - 脱水症や熱中症のリスクが軽減される
    - 水分摂取が習慣化されることで、脱水状態になりにくくなる
    - 夏場の熱中症リスクが軽減される
 - 長期的変化（1年以上）:
  - 救急搬送の軽減により、医療機関の逼迫を防ぐ
    - 予防できる病気で医療機関が逼迫するのを防ぐ
    - これはアプリ単体で実現できる価値ではなく、多くのユーザーが習慣化した結果として期待できる社会的な価値である
    - 飲水習慣が身についておるので、将来的に認知症を発症しても継続できる

## 7.このアプリで実現すること
### 7-1.MVPで作る機能（Must：必須）
1. 新規登録・ログイン機能（Devise）  
  - ユーザーごとに記録を管理
  - 登録時にメールアドレス、パスワード、体重を登録
  - 設定画面でパスワードと体重の変更が行える

2. 体重入力と目標飲水量の自動計算 
  - 体重を入力すると、目標水分摂取量が自動で計算（体重 × 30ml）
  - 体重は、新規登録画面で初期設定し、設定画面で再設定が行える

3. 水分摂取記録
  - 新規登録後、ログイン後は自動的に記録画面に遷移する
  - ワンタップ記録（コップ1杯 = 200ml固定）
  - 記録画面に1週間分の水分摂取記録を提示
    - 縦列に各日付、横列に時間（8時、１２時、１７時）、真ん中にそれぞれ200mlボタンを配置
    - 飲水していない時は灰色の200mlボタンを押さない
    - 飲水時は灰色の200mlボタンを押し緑色に変更する
    　（ヘッダー部分に緑色で「飲水を記録しました」と３秒間表示）
    - 修正時に緑色の200mlボタンを再度押すことで灰色変更する
    　（ヘッダー部分に赤色で「飲水記録を削除しました」と３秒間表示）

   MVP版での運用方法
  - 時間的な制約により通知機能をMVPで実装できなかったことから、MVPでは通知機能をアプリ側では実装せず、ユーザーが携帯のアラーム機能を使用して、1日3回（朝8時、昼12時、夕方17時）にアラームを設定する
  - アラームが鳴ったら、ユーザーがログインして記録画面に遷移し、「200ml」ボタンをタップして記録完了

## 8. 検証
#### 8-1.検証の概要
- 検証対象者：2名（60歳代、70歳代）
- 検証期間：2026年6月27日〜28日（2日間）
- 最大の気づき：
「若者にとって当たり前のUIは、高齢者にとって高い壁になる」ことを痛感。実際の高齢者テストで、ログイン操作に4〜5分かかり、小さな文字やボタンの押しづらさが離脱に直結することを実証ベースで発見。これが、「自動ログイン（トークン認証）」の導入や「文字サイズの基本的な18px以上」という、本アプリのコアなUX改善の原動力となりました

#### 8-2.仮説の検証結果
| 仮説 | 検証結果 | 判定 |
|------|---------|------|

| ②通知機能は継続に効果的か | 通知に気づき、水分摂取のきっかけになった | 有効 |
| ③UI/UXは身体的特徴に配慮できているか | 文字サイズが小さく、ボタンに枠線がないため押しづらかった | 課題あり |

3. ログイン操作に時間がかかる ：4〜5分かかった

  - ボタンに枠線を追加（border: 2px solid）
  - ボタンの余白を拡大（padding: 16~20px）
  - ボタン間の間隔を拡大（margin: 12px）
  - ボタンに薄い影を追加（box-shadow、min-height: 60px）

4. トークン認証（自動ログイン）
  - メールのリンクには、ユーザーを識別するセキュアなトークンを含める
  - ユーザーがメールのリンクをタップすると、自動的にログイン状態になり、記録画面に遷移
  - セキュリティ要件の担保
    - ワンタイムトークン化:トークンは一度使用された時点で無効化（DB上で破棄またはフラグ更新）し、万が一のなりすましやリプレイ攻撃を防止する
    - 有効期限の設定:トークンの有効期限は発行後「24時間」とし、期限切れのトークンからのアクセスは自動的に拒否する
    - 推測困難性の確保:Railsの `has_secure_token` を活用し、総当たり攻撃（ブルートフォース）で推測されない十分な長さのランダム文字列を生成する
    - メール転送・盗み見リスクへの配慮: トークン経由でアクセスできるのは「飲水記録」「カレンダー画面」のみに限定し、その他の個人情報ページへは直接遷移させない設計とする（重要な設定変更時は再度パスワード入力を要求）

## 9.このアプリの懸念点とその対策
懸念点①：メール通知が迷惑メールフォルダに入ってしまう
何が問題になりそうか：
  - メール通知が迷惑メールフォルダに振り分けられると、ユーザーがリマインドを受け取れない可能性がある
  - 一部のメーラーで、URLがリンクにならないケースがある（特に古い機種やPC）
なぜそう思うか：
  - 定期的に送信されるメールは、スパムと判定されやすい
  - iOSの一部の機種やPC含めて一部のメーラーで、URLがリンクにならないケースがある
そのために考えている対策：
Should版：
  - 初回登録時に「メールが届かない場合は迷惑メールフォルダを確認してください」と案内する
  - メール内に「リンクが表示されない場合は、以下のURLをコピーしてブラウザに貼り付けてください」という文言を追加する
  - リンクの下に、URLをテキストで表示する
  - SendGridやMailgunなどの信頼性の高いメール配信サービスを使用する
  - 送信元ドメインの認証（SPF、DKIM、DMARC）を設定して信頼性を高める


懸念点②：ユーザーが水分摂取記録を入力し忘れる
何が問題になりそうか：
  - 水分摂取記録を入力しないと、達成状況が正しく反映されず、継続のモチベーションが下がる
なぜそう思うか：
  - 高齢者は、記録を忘れやすい
そのために考えている対策：
MVP版:
  - 記録入力を簡単にする（ワンタップで記録完了）
  - 水分摂取量は「コップ1杯 = 200ml」と固定し、選択の手間を省く
  - トップページに記録方法を提示し、わかりやすいようにする
  - 新規登録画面やログイン画面下面から直接記録画面に遷移できるようにする
Should版：
  - 水分摂取量の選択肢を増やす：150ml / 200ml / 250ml　＊コップ1杯＝200ml
Could版（将来的に追加）：
  - 就寝時間前に「今日の記録を確認しましょう」というリマインドメールを送る


懸念点③：目標水分摂取量の計算が実態と合わない可能性
何が問題になりそうか：
  - 体重だけで目標水分摂取量を計算すると、個人の生活習慣や健康状態に合わない可能性がある
なぜそう思うか：
  - 運動量、気温、持病などによって必要な水分量は変わる
そのために考えている対策：
MVP版：
  - 「体重 × 30ml」というシンプルな計算式を採用する
  - 「医師に相談してください」という注意書きを表示する
Could版：
  -　必要時、運動量や気温を考慮したカスタマイズ機能を追加する


懸念点④：実際に水を飲んでいなくても記録できてしまう
何が問題になりそうか：
  - メール通知のリンクをタップするだけで記録が完了すると、実際に水を飲んでいなくても記録できてしまうので「水分摂取を習慣化する」という目的が達成できない
なぜそう思うか：
  - 記録が「実際の行動」を反映しない場合、カレンダーの達成状況が「嘘」になってしまう
  - ユーザー自身も「記録したから飲んだことにしよう」と自己欺瞞に陥る可能性がある
そのために考えている対策：
MVP版：
1. シンプルな記録フロー
  - 携帯のアラーム通知後、ログインして、記録画面に遷移
  - 記録画面で「200ml」ボタンをタップすると記録が完了（ワンタップ）
  - 確認メッセージは表示しない（操作のハードルを下げるため）
2. 記録に１週間の記録を提示することで達成状況の可視化
  - 達成状況を可視化することで、ユーザー自身が「本当に飲んだか」を意識できる
3. 継続性を重視した設計
  - 記録のハードルを下げるため、ワンタップで記録完了できる仕組みを維持
  - 高齢者にも理解しやすいシンプルな操作性を保つ
  - 「記録すること」自体が、水分摂取を意識するきっかけになる
Could版：
1. 就寝前の振り返りメールで達成状況を可視化する
  - 就寝前に振り返りメールを送信し、今日の記録(回数、合計水分摂取量、達成率)を表示
  - 振り返りの機会を提供することで、ユーザー自身が「本当に飲んだか」を意識できる
2. 「後で飲む」機能と再リマインド
  - 記録時に「今すぐ飲んで記録」「後で飲む」を選択できる
  - 「今すぐ飲んで記録」：水分摂取記録が1件追加される
  - 「後で飲む」：記録されず、30分後に再度リマインドメールが届く
  - この機能により、記録の信頼性が高まる
3. 連続達成日数のバッジ機能
  - 連続達成日数に応じてバッジを付与（例：7日連続達成で「1週間バッジ」）
  - 正直な記録を続けることで達成感を得られる仕組みを作る
4. 記録の信頼性を高める工夫
  - 記録時に「飲んだ時刻」を自動記録し、不自然な記録パターン（短時間に複数回記録など）を検知
  - 不自然なパターンが検出された場合、「本当に飲みましたか？」というメッセージを表示
  - ただし、ユーザーを疑うような表現は避け、あくまで「確認」として提示する
限界と割り切り：
- アプリ上で「実際に飲んだかどうか」を完全に強制・証明することは技術的にもプライバシー的にも不可能
- 本アプリの本質は「監視・強制」ではなく、「認知のトリガー（引き金）」と「カレンダーによる客観的な可視化」にある
- 「記録すること」自体が、高齢者の脳に水分摂取を意識させる最大のトリガーとなり、周囲（家族・ケアマネ）にとっても「今日動いているか」の緩やかな生存確認・セーフティーネットとして機能する


懸念点⑤：パスワード入力が高齢者にとって負担になる
何が問題になりそうか：
  - 大文字小文字の入力切り替え方法がわからない
  - 何を入力したか状態がわからない（パスワードが●●●で表示されるため）
  - パスワードを忘れやすい
なぜそう思うか：
  - 高齢者はパスワード入力でつまずきやすい
  - 事前検証で、パスワード入力の負担を確認する
そのために考えている対策：
MVP版：
  - 最低限のパスワード要件（8文字以上）
Should版：
  - パスワード入力の負担を確認する（検証）
  - パスワード入力画面に「パスワードを表示する」チェックボックスを追加
  - トークン認証（自動ログイン）を実装し、パスワード入力の負担を軽減【重要】
Could版：
  - パスワードリセット機能を用意
  - 初回登録時に「パスワードを忘れた場合の対処法」を案内する
  - パスワードの強度チェックを緩和（最低8文字、英数字のみでOK）
  - 大文字小文字の区別をなくす（すべて小文字として扱う）
  - 記号の入力を不要にする
  - パスワード入力時に、「入力した文字」を表示する（例：「a」を入力したら「a」と表示）
  - パスワード入力時に、大文字小文字の入力切替方法を案内する（例：「Shiftキーを押しながら入力すると大文字になります」）
  - パスワード入力時に、何を入力したか状態がわかるようにする（例：「8文字入力しました」と表示）
  - ネイティブアプリ化を検討
    - 一度ログインすればパスワード入力不要
    - 生体認証（指紋認証・顔認証）も利用可能
    - プッシュ通知が使える
  - ただし、開発コストが大幅に増加するため、MVP版での検証結果を踏まえて判断する


懸念点⑥：実際に使ってもらえるか検証したい
何が問題になりそうか：
  - 高齢者にとって「通知」や「ログイン画面を経由する操作」で飲水習慣が身につきそうか、検証したい
なぜそう思うか：
  - 実際に使ってもらわないと、想定通りに機能するかわからない
  - 高齢者向けのアプリは、操作のハードルが少しでも高いと使われなくなる可能性がある
そのために考えている対策：
Should版を開始時に検証：
1. MVP版の状態で検証を行い、高齢者にとってどの部分が継続するために負担になるのか把握する
  - ログイン画面を経由する操作が、高齢者にとって負担になるか確認する
  - 通知と記録で飲水習慣が継続して行えそうか確認する
2. 事前検証後の対応
  - 検証結果をもとに、Should版の仕様を調整する

### 10-3.技術的な工夫・変遷（開発の背景）
1. DBサービスの変更（Renderの無料DB から Neon(PostgreSQL 16) へ）
   - 変更理由： MVPの実装期間が2週間と短期間であったため、初期段階はスピードを最優先してRenderの無料DBを採用。その後、Should版（本リリース）のタイミングで、Renderの無料DBが持つ30日間でのデータ削除・停止制限をクリアし、中長期的な無期限運用とサーバーレスならではの安定した可用性を確保するため、Neonへ計画的に移行
2. 認証gemの変更（Sorcery から Devise へ）
   - 変更理由： Sorceryは長年メンテナンスが停滞しており、最新環境への追従やセキュリティ面の懸念があったため、アプリの安全性と保守性を最優先して標準的で堅牢なDeviseに変更
3. メール配信基盤におけるポート制限対策（SMTP から ResendのHTTP API方式へ）
   - 変更理由： Render環境では通常のSMTPポート（587番など）が制限されるリスクがあるため、インフラ起因の送信トラブルを回避し、確実な到達率を担保できるResendのHTTP API方式（HTTPS/443番）を採用
4. 独自ドメインとメールセキュリティ基盤（Cloudflare ＋ Resend）の構築
   - 変更理由： 単にアプリをデプロイするだけでなく、`mizumo-app.com` の独自ドメインを取得し、Cloudflare（DNS・Email Routing・プロキシ保護）とResend（SPF/DKIM/DMARC認証）を連携させることで、実務レベルのセキュアなメール送受信・信頼性を担保した環境を構築
5. 独自ドメイン（`mizumo-app.com`）の導入とRailsのホスト許可設定
   - 変更理由： Renderのデフォルトサブドメインから独自のブランディング用ドメインへ移行するため、CloudflareでのDNS設定（CNAME/Aレコード）とRenderのカスタムドメイン機能を連携。それに伴い、Rails 7の標準セキュリティ機能であるHost Authorizationに対応するため、`config/environments/production.rb` の `config.hosts` に `mizumo-app.com` およびホスト名を明示的に許可し、不正なリクエストをブロックしつつ正しくアクセスできる環境を構築
6. インフラ制約を考慮した外部SaaS（Upstash / Resend）の積極活用
   - 変更理由：Renderの無料プラン環境における「永続ストレージ/Redisの欠如」や「SMTPポート制限」というインフラ上の制約に対し、セルフホストではなくサーバーレスな外部SaaS（Upstash、Resend）を組み合わせるアーキテクチャを採用。インフラ起因の障害リスクを最小化し、ゼロコスト運用と実務水準の安定性を両立

### 10-4.開発で最も苦労した点と学び（またはインフラ構築の裏側）
【背景】
当初は「問い合わせ画面のメール送信」を軽く考えていましたが、それをきっかけに独自ドメイン（mizumo-app.com）の導入を決断したことで、DNS設定、メールセキュリティ（SPF/DKIM/DMARC）、Renderのポート制限、SMTPからHTTP APIへの移行といった、想定外のインフラ構築の沼に約1週間ハマりました。

【乗り越え方】
しかし、途中で妥協しなかったのには明確な理由があります。このアプリの向こう側には「確実にリマインドを待っている高齢者」がおり、高齢者向けアプリにおいて『メールが届かない』『通知が漏れる』は利用者の安否に直結する致命傷になるからです。
だからこそ、単なる失敗で終わらせず、CloudflareとResendを徹底的に調べ上げ、実務レベルのセキュアなメール配信基盤を独力でやり切りました。
この1週間の沼を通じて、単に「動くコードを書く」だけでなく、「本番環境を見据えたインフラのセキュリティなどの組み合わせた堅牢なアーキテクチャ設計」の重要性を身をもって深く学ぶことができました。

## 11.今後の展開・発展の方向性
### 11-1.全体像
- 個人での『水分摂取の習慣化』
- 高齢者と周囲の人々を繋ぐ安否確認のセーフティーネット（ハブ）へと発展

### 11-2.具体的な流れ
- 高齢者が飲水量ボタン押すことで周囲の人々に安否確認が行える
  - 通知有り：生存確認
  - 通知無し：高齢者の安否確認後を連絡もしくは直接確認し、熱中症などの早期発見・重症化の防止に繋げる

### 11-3.事業計画（短期的な目標・マネタイズ）
- 初期フェーズ（無料期間）：
  - 1つの介護事業所（居宅介護支援事業所やデイサービス等）と深く連携し、実証実験を行う
  - まずはデザインの微調整やシステム安定性を最優先するため、初期は完全無料で提供。現場のリアルなデータを集め、サポートなしでも高齢者が回せるUI/UXにブラッシュアップを行う
- 1つの事業所への集中アプローチ：
  - 初期は不特定多数への営業ではなく、1つの介護事業所（居宅介護支援事業所やデイサービス等）に絞ってアプローチを行う。密に連携をとることで、完全独居などの見守りが行き届きにくい層も含めた実証実験を行う
- スモール課金への移行：
  - 価値を十分に実感していただけた段階で、1人あたり月額500円程度のスモール課金へ移行（※移行時は利用規約の提示と事前メール通知を徹底）。

### 11-4.事業計画(長期的な目標)
- 事業所を１つずつ増やす
- 「高齢者・家族・ケアマネジャーの三者を繋ぐハブ（架け橋）」となるようなサービスへと発展させ、高齢者本人の自立した生活を支えつつ、周囲のサポート体制とも緩やかにつながる環境を構築する
- 心臓や腎臓疾患等の飲水制限のある患者様の管理、内服管理に伴う水分管理、入院・退院指導時の脱水予防サポートとしての展開を見据える
- 自治体や社会福祉協議会とタイアップし、行政の「見守り事業の一環」として導入も見据える

### 11-5. ビジネスモデル
- B to B to C モデル（事業者・ケアマネジャー経由の導入）
  - 事業者（デイサービスやケアマネ事業所等）が導入窓口となり、高齢者またはその家族にサービスを提供
  - 費用負担: 初期は無料、検証完了後は見守りの付加価値として事業者または遠方の子ども世代（BtoFamily）に月額500円で負担。
  - 完全独居・支援が必要な層へのアプローチの工夫: 
    - 完全独居の高齢者本人が自力で初期設定を行うのはハードルが高いため、初期のアプローチ先である「1つの介護事業所」のケアマネジャーや訪問スタッフに協力依頼を行い、自宅訪問時に初期設定（メールアドレス・通知設定）を代理で行う。これにより、孤立しがちな層もセーフティーネットに巻き込むことが可能になる
